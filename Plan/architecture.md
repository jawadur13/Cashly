# Cashly — Architecture

## 1. Stack Overview

| Layer | Choice | Why |
| --- | --- | --- |
| Framework | Next.js 15 (App Router) + TypeScript | Full-stack, PWA-friendly, Appwrite has first-class Next.js docs |
| Backend | Appwrite Cloud | Hosted DB + Auth, no server code to write, fine-grained permissions |
| Auth | Appwrite Auth (email/password) | Built-in sessions, recovery, verification |
| Database | Appwrite Database (collections) | Document store, fits the small relational-ish model |
| Styling | Tailwind CSS v4 | Utility-first, design tokens map directly |
| State/data | Appwrite JS SDK (client) + React Context + custom hooks | No heavy state library needed at this scope |
| Icons | `lucide-react` | Consistent, light, tree-shakeable |
| PWA | Serwist (`@serwist/next`) | Modern, maintained `next-pwa` replacement |
| Money | `Intl.NumberFormat` | Native, no dependency |
| Lint/Format | ESLint + Prettier | Default Next.js ESLint, Prettier config |

Deliberately avoided: Redux/Zustand/React Query, ORM, REST API layer. The
Appwrite SDK talks to Appwrite Cloud directly from the client. This keeps v1
small. If complexity grows, TanStack Query can be added later without rework
because all data access goes through thin hooks.

## 2. Data Flow

```
Browser (React client components)
   │  appwrite SDK
   ▼
Appwrite Cloud
   ├── Auth   (sessions, users)
   └── DB     (transactions, categories collections, user prefs)
```

- All reads/writes happen in client components via hooks (below).
- Server components are used for static pages and layout only (they render the
  auth-gated shell; data still loads client-side).
- Security: Appwrite permission rules per document (owner-only read/write). The
  client never sees other users' data.

## 4. Appwrite Setup (Cloud console, done once)

1. Create project **"Cashly"** on appwrite.io.
2. Note Project ID + API endpoint (default `https://cloud.appwrite.io/v1`).
3. Enable email/password auth method.
4. Create database → two collections: `transactions`, `categories`.
   - Collection schemas + indexes: see `database-schema.md`.
5. `.env.local`:
   ```
   NEXT_PUBLIC_APPWRITE_ENDPOINT=https://cloud.appwrite.io/v1
   NEXT_PUBLIC_APPWRITE_PROJECT_ID=<project-id>
   ```
   (`NEXT_PUBLIC_` because the SDK runs in the browser.)

## 5. Client SDK Wrapper

`src/lib/appwrite/client.ts`

```ts
import { Client, Account, Databases } from 'appwrite'
export const client = new Client()
  .setEndpoint(process.env.NEXT_PUBLIC_APPWRITE_ENDPOINT!)
  .setProject(process.env.NEXT_PUBLIC_APPWRITE_PROJECT_ID!)
export const account = new Account(client)
export const databases = new Databases(client)
```

Central place for endpoints so app code never touches raw SDK init.

`src/lib/appwrite/permissions.ts` — helper to build owner permission sets:
- Transactions: `[Permission.read(userId), Permission.update(userId), Permission.delete(userId)]`
- Custom categories: same as transactions.
- Predefined categories: created once server-side (console or setup script)
  with default public-read permissions (read only for everyone, no write).

## 6. Auth Strategy

- Appwrite session stored in its own cookies (handled by SDK).
- `AuthProvider` (context): subscribes to `account.get()` on mount to know
  logged-in state, exposes `user`, `status` (`loading | authenticated |
  anonymous`), `signIn`, `signUp`, `signOut`.
- Guard: `src/app/app/layout.tsx` — if `status !== authenticated` show a loader
  while checking, then redirect to `/auth/login`. Auth pages redirect to `/app`
  when authenticated.
- Session persistence: Appwrite cookies survive refresh by default (client SDK
  reads `a_session_*` cookie); no extra work needed.
- User prefs (default currency, display name) stored via Appwrite **User Prefs**
  (key `defaultCurrency`) — no extra collection required.
  - Read: `account.getPrefs()`, write: `account.updatePrefs()`.
  - `SettingsProvider` exposes `prefs`, `setDefaultCurrency`.

## 7. Data Access Hooks

Thin hooks encapsulate all Appwrite calls so components stay clean:

- `useAuth()` — from AuthProvider.
- `useUserPrefs()` — default currency; also returns the list of supported
  currencies from `lib/currency/currencies.ts`.
- `useTransactions(filters)` — list for current user with `type` and
  `currency` queries; exposes `refetch`.
- `useCategories()` — predefined + user's custom categories; exposes `add`,
  `remove`.
- CRUD functions live in `lib/appwrite/collections.ts`:
  `listTransactions`, `createTransaction`, `updateTransaction`,
  `deleteTransaction`, `listCategories`, `createCategory`, `deleteCategory`.

All queries are keyed off `user.$id` in the Appwrite `queries` (see schema).

## 8. Data Loading & Mutations Pattern

- **Load:** `useEffect` + async hook functions, component-local `loading` /
  `error` state. Skeleton UI while loading.
- **Mutate:** call hook function → optimistic update optional (v1: just
  refetch on success) → toast feedback → navigate.
- Keep it simple; no server cache layer in v1.

## 9. PWA (Serwist)

- Install `@serwist/next`; config in `next.config.ts`:
  - register service worker
  - precache app shell (static assets)
  - runtime cache: Appwrite API responses (network-first for data), Google
    fonts (stale-while-revalidate)
- Manifest at `src/app/manifest.ts` (Next.js API) with icons from
  `public/icons/`.
- Offline behaviour: app shell loads; data pages show cached or "offline"
  state. Full offline data is out of scope.
- iOS: add `<meta name="apple-mobile-web-app-capable">` etc. in root layout.

## 10. Environment / Tooling

- `npm run dev`, `npm run build`, `npm run start`, `npm run lint`.
- Node LTS ≥ 20.
- Version control: git repo initialised at project root; `.gitignore` excludes
  `.env.local`, `.next`, `node_modules`, sw-generated files as appropriate.

## 11. Non-Functional Requirements

- **Performance:** PWA should feel instant on mobile; list pages use pagination
  (`limit` + `offset` via Appwrite queries, page size 20).
- **Security:** owner-only permissions, `NEXT_PUBLIC_*` for browser-safe
  config only, no secrets in client code.
- **Correctness:** server-side-consistent validation on write hooks (trim,
  type check, positive amount), format validation in forms.
- **Accessibility & i18n:** see `design.md`. UI in English; amounts use
  browser locale.
